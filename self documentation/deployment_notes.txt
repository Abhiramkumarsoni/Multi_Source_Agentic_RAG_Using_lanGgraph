1. THE BIG PICTURE - HOW DEPLOYMENT WORKS
================================================================================

Your code travels through 3 places:

    YOUR COMPUTER      →      GITHUB          →      HUGGING FACE
    (Where you code)      (Storage/Backup)       (Where app runs online)

What happens at each stage:
---------------------------
• YOUR COMPUTER: You write code, test locally, commit changes
• GITHUB: Stores your code, runs automation (CI/CD)
• HUGGING FACE: Builds container, hosts your app for the world

================================================================================
2. WHAT IS DOCKER?
================================================================================

SIMPLE DEFINITION:
------------------
Docker is like a "shipping container" for your application.
It packages your app + all its dependencies into one portable unit.

ANALOGY:
--------
Think of it like moving houses:
• Without Docker: You move each item separately, some things break
• With Docker: Everything goes in one container, nothing breaks

COMPARISON TABLE:
-----------------
┌─────────────────────────────┬───────────────────────────────────────────┐
│ Without Docker              │ With Docker                               │
├─────────────────────────────┼───────────────────────────────────────────┤
│ "Works on my machine!" 🤷   │ "Works everywhere!" ✅                    │
│ Different Python versions   │ Same Python version everywhere            │
│ Missing dependencies        │ All dependencies included                 │
│ Complex setup on new server │ Just run the container                    │
└─────────────────────────────┴───────────────────────────────────────────┘

KEY DOCKER CONCEPTS:
--------------------
• IMAGE: A template/blueprint (like a class in programming)
• CONTAINER: A running instance of an image (like an object)
• DOCKERFILE: Instructions to build an image (like a recipe)

3. UNDERSTANDING DOCKERFILE
================================================================================

A Dockerfile is a step-by-step recipe for building your container.

BASIC STRUCTURE:
----------------
┌─────────────────────────────────────────────────────────────────────────────┐
│ # Step 1: Start with a base image (like choosing a foundation)             │
│ FROM python:3.11-slim                                                       │
│                                                                             │
│ # Step 2: Set working directory (like cd into a folder)                    │
│ WORKDIR /app                                                                │
│                                                                             │
│ # Step 3: Copy files into the container                                    │
│ COPY requirements.txt .                                                     │
│ COPY . .                                                                    │
│                                                                             │
│ # Step 4: Install dependencies                                             │
│ RUN pip install -r requirements.txt                                        │
│                                                                             │
│ # Step 5: Expose a port (make it accessible)                               │
│ EXPOSE 7860                                                                 │
│                                                                             │
│ # Step 6: Command to run when container starts                             │
│ CMD ["streamlit", "run", "app.py"]                                         │
└─────────────────────────────────────────────────────────────────────────────┘

LINE-BY-LINE EXPLANATION:
-------------------------
FROM python:3.11-slim
  → "Start with Python 3.11 (slim version = smaller size)"

WORKDIR /app
  → "Create and go into /app folder inside container"

COPY requirements.txt .
  → "Copy requirements.txt from my computer to container"

RUN pip install -r requirements.txt
  → "Run this command to install all dependencies"

EXPOSE 7860
  → "Tell Docker that the app will use port 7860"

CMD ["streamlit", "run", "app.py"]
  → "When container starts, run this command"

HUGGING FACE REQUIREMENTS:
--------------------------
• Must create non-root user (security requirement)
• Must expose port 7860 (HuggingFace default)
• Must use 0.0.0.0 as address (accessible from outside)

4. WHAT IS CI/CD?
================================================================================

DEFINITION:
-----------
CI/CD = Continuous Integration / Continuous Deployment

In simple terms: AUTOMATIC DEPLOYMENT WHEN YOU PUSH CODE

COMPARISON:
-----------
┌─────────────────────────────────┬───────────────────────────────────────────┐
│ WITHOUT CI/CD (Manual)          │ WITH CI/CD (Automatic)                    │
├─────────────────────────────────┼───────────────────────────────────────────┤
│ 1. Code on computer             │ 1. Code on computer                       │
│ 2. Push to GitHub               │ 2. Push to GitHub                         │
│ 3. Go to HuggingFace website    │ 3. DONE! Everything else automatic 🚀    │
│ 4. Upload files manually        │                                           │
│ 5. Wait for build               │                                           │
│ 6. Check for errors             │                                           │
│ 7. Repeat for every change 😫   │                                           │
└─────────────────────────────────┴───────────────────────────────────────────┘

HOW IT WORKS:
-------------
    You push code to GitHub
            ↓
    GitHub Actions detects the push
            ↓
    Runs your workflow file (deploy.yml)
            ↓
    Pushes code to Hugging Face
            ↓
    Hugging Face builds and deploys
            ↓
    Your app is LIVE! 🎉

5. UNDERSTANDING GITHUB ACTIONS (deploy.yml)
================================================================================

GitHub Actions is GitHub's built-in CI/CD system.
Workflow files are stored in: .github/workflows/

ANATOMY OF deploy.yml:
----------------------

┌─────────────────────────────────────────────────────────────────────────────┐
│ name: Deploy to Hugging Face Spaces                                        │
│ └── Name displayed in GitHub Actions tab                                   │
│                                                                             │
│ on:                                                                         │
│   push:                                                                     │
│     branches:                                                               │
│       - main                                                                │
│ └── TRIGGER: Run this workflow when code is pushed to main branch          │
│                                                                             │
│ jobs:                                                                       │
│   deploy:                                                                   │
│     runs-on: ubuntu-latest                                                  │
│ └── ENVIRONMENT: Use a Linux server from GitHub's cloud                    │
│                                                                             │
│     steps:                                                                  │
│       - name: Checkout Repository                                          │
│         uses: actions/checkout@v4                                          │
│ └── STEP 1: Download your code from GitHub                                 │
│                                                                             │
│       - name: Push to Hugging Face Hub                                     │
│         run: |                                                              │
│           git remote add huggingface https://...                           │
│           git push huggingface main --force                                │
│ └── STEP 2: Push code to HuggingFace                                       │
└─────────────────────────────────────────────────────────────────────────────┘

KEY YAML CONCEPTS:
------------------
• name:        → Descriptive name for the workflow/step
• on:          → What triggers this workflow (push, schedule, manual)
• jobs:        → Collection of tasks to run
• runs-on:     → Which operating system to use
• steps:       → Individual tasks within a job
• uses:        → Use a pre-built action (like a library)
• run:         → Run custom shell commands

6. UNDERSTANDING GITHUB SECRETS
================================================================================

WHAT ARE SECRETS?
-----------------
Secrets are encrypted environment variables stored in GitHub.
Used for sensitive data like passwords, API keys, tokens.

WHY USE SECRETS?
----------------
• Never put passwords/tokens in your code!
• Anyone can see your GitHub code
• Secrets are encrypted and hidden

HOW TO CREATE SECRETS:
----------------------
1. Go to your GitHub repository
2. Click "Settings" tab
3. Left sidebar: "Secrets and variables" → "Actions"
4. Click "New repository secret"
5. Enter name and value

OUR SECRETS:
------------
┌────────────────────┬─────────────────────────────────────────────────────────┐
│ Secret Name        │ Purpose                                                 │
├────────────────────┼─────────────────────────────────────────────────────────┤
│ HF_TOKEN           │ HuggingFace access token (for authentication)          │
│ HF_USERNAME        │ Your HuggingFace username                               │
│ HF_SPACE_NAME      │ Name of your HuggingFace Space                          │
└────────────────────┴─────────────────────────────────────────────────────────┘

HOW SECRETS ARE USED IN WORKFLOW:
---------------------------------
In deploy.yml:
    ${{ secrets.HF_TOKEN }}      → Replaced with actual token at runtime
    ${{ secrets.HF_USERNAME }}   → Replaced with: abhiram-soni1
    ${{ secrets.HF_SPACE_NAME }} → Replaced with: multi-source-rag-agent

Example:
    git remote add huggingface https://user:${{ secrets.HF_TOKEN }}@huggingface.co/spaces/...
    
    Becomes at runtime:
    git remote add huggingface https://user:hf_actual_token_here@huggingface.co/spaces/...

7. HUGGING FACE README CONFIGURATION
================================================================================

Hugging Face Spaces reads the TOP of your README.md to configure the Space.

YAML FRONTMATTER:
-----------------
Must be at the VERY TOP of README.md, between --- markers:

┌─────────────────────────────────────────────────────────────────────────────┐
│ ---                                                                         │
│ title: Multi Source Rag Agent    ← Name displayed on HuggingFace           │
│ emoji: 🤖                         ← Icon shown next to name                 │
│ colorFrom: purple                 ← Theme gradient start color              │
│ colorTo: blue                     ← Theme gradient end color                │
│ sdk: docker                       ← HOW to run: docker, streamlit, gradio   │
│ pinned: false                     ← Pin to top of your profile?             │
│ license: mit                      ← License type                            │
│ app_port: 7860                    ← Port your app runs on                   │
│ ---                                                                         │
│                                                                             │
│ # Your README content starts here...                                        │
└─────────────────────────────────────────────────────────────────────────────┘

SDK OPTIONS:
------------
• sdk: docker     → Use Dockerfile to build (most flexible)
• sdk: streamlit  → HuggingFace provides Streamlit environment
• sdk: gradio     → HuggingFace provides Gradio environment

We used sdk: docker because:
• Full control over environment
• Can install any dependencies
• Works with complex applications

8. GIT LFS (LARGE FILE STORAGE)
================================================================================

WHAT IS GIT LFS?
----------------
Git LFS = Git Large File Storage
Extension that handles large files like PDFs, images, videos, datasets.

WHY DO WE NEED IT?
------------------
• Regular Git stores entire file history
• Large files make repository HUGE
• Cloning becomes very slow
• HuggingFace REJECTS large binary files without LFS

HOW IT WORKS:
-------------
Normal Git:
    [Your Repo] → [Full PDF file stored in history]
    
With LFS:
    [Your Repo] → [Small pointer file] → [PDF stored in LFS server]

COMMON GIT LFS COMMANDS:
------------------------
git lfs install                  → Enable Git LFS for your repository
git lfs track "*.pdf"            → Tell LFS to track all PDF files
git lfs ls-files                 → List files tracked by LFS
git lfs pull                     → Download LFS files
git lfs migrate import --include="*.pdf" --everything
    → Convert existing PDFs in history to LFS

THE ERROR WE FACED:
-------------------
"Your push was rejected because it contains binary files."
"Offending files: data/Agent Quality Whitepaper.pdf"

SOLUTION:
---------
1. git lfs install
2. git lfs track "*.pdf"
3. git lfs migrate import --include="*.pdf" --everything
4. git push origin main --force
